# Участие в разработке devassist

Спасибо, что вкладываетесь в проект! Ниже — короткий регламент, чтобы код
оставался единообразным и предсказуемым.

## Быстрый старт для разработчика

```bash
git clone <repo-url> devassist
cd devassist

make dev        # = uv sync: .venv + пакет (editable) + dev-группа
cp .env.example .env   # и впишите GIGACHAT_ACCESS_KEY

make test       # быстрые офлайн-тесты
```

Если `make` недоступен, эквиваленты команд см. в `Makefile` (все через `uv run`).

## Зависимости

- Менеджер — [uv](https://docs.astral.sh/uv/). Runtime-зависимости — в
  `[project.dependencies]`, инструменты разработчика — в `[dependency-groups] dev`.
- Добавление: `uv add <пакет>` / `uv add --dev <пакет>`; `uv.lock` коммитится вместе
  с `pyproject.toml`. `make check` проверяет, что лок актуален (`uv lock --check`).

## Рабочий процесс

1. Создайте ветку от актуальной основной: `feature/<кратко>` или `fix/<кратко>`.
2. Вносите изменения небольшими логичными коммитами.
3. Перед пушем прогоните `make check` (линт + тесты).
4. Откройте merge/pull request, опишите **что** и **зачем**.

## Стиль кода

- Python ≥ 3.10, type hints обязательны для публичных функций.
- Форматирование и линтинг — [ruff](https://docs.astral.sh/ruff/):
  `make lint` (проверка) и `make format` (автоформат).
- Длина строки — 100 символов.
- Сообщения коммитов — в духе [Conventional Commits](https://www.conventionalcommits.org/):
  `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`.

## Тесты

- Новый функционал сопровождается тестами; правки багов — регрессионным тестом.
- Офлайн-тесты не должны ходить в сеть. Сетевые тесты помечайте маркером `live`
  (см. `pyproject.toml`), они пропускаются без `GIGACHAT_ACCESS_KEY`.
- Запуск: `make test` (офлайн, быстро) / `uv run pytest -m live` (живые).

## Безопасность и секреты

- **Никогда** не коммитьте `.env` и реальные ключи. `.env` в `.gitignore`.
- Новые секреты добавляйте в `.env.example` с пустым значением и комментарием.
- Изменяя слой безопасности (`security.py`), не ослабляйте песочницу и
  подтверждения без обсуждения с командой.

## Архитектурные правила

- Ядро (`agent/`, `llm/`, `tools/`, `project/`) не импортирует `ui`, `cli`, `rich`
  и `prompt_toolkit` — проверяется `tests/test_layering.py`. Всё, что видит
  пользователь, передаётся через `AgentEvents` (`agent/events.py`). Парные события
  (`on_stream_start/end`, `on_tool_start/end`) вызываются в `try/finally` — UI
  полагается на то, что конец придёт всегда.
- В UI одновременно живёт не больше одной временной области (`Console._start_live`
  останавливает предыдущую); печать во время неё — через `Console._print_above_live`,
  иначе поток анимации может стереть напечатанное. Цвета — только из `ui/theme.py`.
- `Config` неизменяем; состояние времени выполнения (текущая модель, история)
  живёт в `Agent`.
- Конструкторы не обращаются к файловой системе и сети; служебная папка
  `.devassist/` создаётся только через `Workspace.ensure_data_dir()`.
- Правила игнорирования файлов — только в `project/files.py` (служебные каталоги)
  и `project/gitignore.py` (`.gitignore`); обходите файлы через `walk_files`.

## Добавление нового инструмента

- Наследник `Tool` (`tools/base.py`), параметры — pydantic-модель (JSON-schema
  генерируется автоматически). Не используйте `ge`/`le` и подобные ограничения в
  `Params` — совместимость таких схем с GigaChat не проверена; ограничивайте
  значения в `run()`.
- `risk()` — уровень риска; для `WRITE`/`DANGEROUS` агент запросит подтверждение.
- `preview()` — `Display` для показа перед подтверждением; если операция
  невыполнима, бросьте `ToolError` — она не будет ни подтверждаться, ни запускаться.
- `run()` — возвращает `ToolResult`; ожидаемые ошибки — `ToolError` (уходят модели).
- `describe()` — краткое описание вызова для UI (по умолчанию — путь/команда/шаблон).
- Вложенные pydantic-модели в `Params` допустимы: ссылки `$ref` подставляются в
  схему (`_clean_schema`), `$defs` в неё не попадают.
- Нужен ответ пользователя — используйте `ctx.ask_user` (как `tools/ask_user.py`);
  `None` в контексте или `QuestionsUnavailable` — спросить некого.
- Внешние процессы запускайте только через `tools/process.run_process`.
- Зарегистрируйте инструмент в `build_default_registry()`.
- Нужны знания о структуре кода — открывайте `ProjectIndex(ctx.workspace)` и
  обновляйте его (`refresh()`, для одного файла/каталога — `refresh(path)`) перед
  запросом, как `tools/index.py`; ошибки `INDEX_ERRORS` превращайте в `ToolError`.

## Индекс проекта

- Новый язык — расширения в `EXTENSIONS` и правила в `_RULES`
  (`project/symbols.py`) плюс пример в `tests/test_symbols.py`.
- Меняя схему базы (`project/index.py`), увеличьте `SCHEMA_VERSION` — старый индекс
  будет пересоздан автоматически.

## Добавление LLM-провайдера

- Реализуйте `LLMProvider` (`llm/base.py`): `complete()` (и по возможности
  `stream()`), принимающие `model=` на вызов и возвращающие `AssistantTurn` с
  `Usage`.
- Любые ошибки обращения бросайте как наследника `LLMError` — CLI ловит только его.

## Слеш-команды

- Новая команда — `SlashCommand` в `cli/commands.py`, регистрация в
  `default_commands()`; справка, подсказки баннера и автодополнение ввода
  строятся автоматически.

Подробности архитектуры — в `README.md`.
